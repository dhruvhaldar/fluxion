## 2024-03-24 - Optimizing Red-Black SOR and Jacobi Iterative Solvers
**Learning:** In tight numerical loops within Python/NumPy (like solving the Pressure Poisson Equation), creating intermediate arrays and performing whole-grid operations (e.g., computing `np.max(np.abs(p_new - p_old))` on every iteration to check convergence) can consume 20-30% of solver time. Also, using advanced boolean indexing (`p_new[mask] = ...`) creates implicit array copies.
**Action:** Optimize convergence checks by evaluating them only periodically (e.g., `if it % 50 == 0`) rather than on every iteration. Use `np.putmask(arr, mask, values)` for in-place conditional updates instead of boolean indexing, yielding a ~2-3x speedup in SOR sweeps.

## 2026-03-25 - Avoiding Implicit Temporary Arrays Before Masking
**Learning:** Even when using `np.putmask` for efficient conditionally updated slices, creating the update array via expressions like `(1 - omega) * p_slice + p_gs_red` generates an implicit temporary array the size of the entire domain grid. In tight numerical solver loops like the Red-Black SOR inner loop, this memory allocation becomes a significant bottleneck.
**Action:** Use in-place operators on existing arrays (e.g., `p_gs_red += (1 - omega) * p_slice`) before applying `np.putmask`, which avoids creating a third full-sized temporary array. This specific optimization can cut iteration time by an additional ~45%.

## 2026-03-26 - Replacing Boolean Indexing with np.where in FVM
**Learning:** In FVM convection schemes like Upwind and QUICK, advanced boolean indexing (`val[mask] = phi_L[mask]`) creates multiple implicit array copies under the hood. Replacing these with `np.where(mask, phi_L, phi_R)` provides a ~3-5x performance improvement, because `np.where` processes the arrays fully in C and avoids the temporary array creations associated with boolean indexing.
**Action:** When conditionally filling arrays based on a boolean mask, prefer `np.where()` over boolean array indexing (`arr[mask] = val`), particularly in tight numerical functions called frequently like convection term calculations.

## 2026-03-30 - Swapping solvers vs. Optimizing internal loops
**Learning:** In the Navier-Stokes FVM solver, swapping the iterative Jacobi solver for the Pressure Poisson Equation (PPE) with the Red-Black SOR solver caused accuracy degradations (failing mass conservation tests). Identical iteration counts and tolerances do not yield identical internal convergence quality for different algorithms handling Neumann boundaries. However, pre-computing slice views (e.g. `p[2:, 1:-1]`) and alternating their references entirely eliminates internal loop overhead safely.
**Action:** When optimizing PDE iterative solvers, prefer algorithmic-safe loop optimizations (like view reference swapping) over swapping entire numerical algorithms unless the new algorithm's exact error and boundary behaviors are thoroughly validated against the physics tests.

## 2026-03-31 - Factoring equations to reduce numpy ufuncs
**Learning:** In tight iterative FVM solvers using numpy arrays (like Jacobi or SOR), each numpy operation (e.g. `np.add`, `np.multiply`) requires a full array traversal which is memory-bandwidth bound. While using in-place operations (`out=`) avoids allocating new memory, the sheer number of array traversals is still a bottleneck.
**Action:** Mathematically factor out common multipliers in finite-difference stencils to reduce the total number of numpy operations per iteration. For example, factoring out `mult_x` from the X and Y diffusion terms reduces the operation count from 6 ops to 5 ops per iteration, yielding a ~30-40% speedup in solver time, especially on square grids where the aspect ratio multiplier evaluates to 1.0 and can be conditionally skipped.

## 2024-04-01 - Avoiding Implicit Temporaries in Convergence Checks
**Learning:** In tight iterative loops (such as convergence checks like `np.max(np.abs(p_new - p_old))` in Jacobi/SOR solvers), evaluating the check creates multiple whole-grid temporary arrays internally (`p_new - p_old`, and the `abs()` of that). This causes high memory bandwidth overhead even when executed periodically (e.g., every 50 steps).
**Action:** Pre-allocate a full-sized array buffer outside the loop (e.g. `tmp_full = np.zeros_like(p)`) and use in-place ufuncs (`np.subtract(p_new, p_old, out=tmp_full)`, `np.abs(tmp_full, out=tmp_full)`) to compute convergence metrics to eliminate implicit allocations.

## 2024-04-10 - Optimizing Temporary Array Use and Convergence Frequency
**Learning:** In tight iterative loops in FVM solvers (`solve_jacobi`, `solve_sor`), even when mathematical operations are done in place, allocating partial temporary slices (like `tmp_y`) and doing convergence checks too often acts as a significant bottleneck.
**Action:** Eliminate the temporary array completely by accumulating directly into the final target slice view (e.g. `p_new_center`). Increase `check_interval` dynamically or use a higher value (like 200 instead of 50) when the problem space requires thousands of iterations, preventing unnecessary convergence check computations.

## 2026-04-12 - Python Loop Overhead vs Implicit Array Allocations
**Learning:** While using sequential in-place operators (`np.add(..., out=p)`, `p += ...`, `p *= ...`) avoids allocating full-grid temporary implicit arrays during mathematical evaluations, doing so inside tight iterative numerical loops (like `solve_jacobi` and `solve_sor`) incurs significant Python interpreter overhead for function wrapping. On the relatively small grid sizes used in this FVM solver (e.g., 64x64 or 128x128), this Python loop overhead drastically outweighs the memory bandwidth cost of implicit temporary array creation.
**Action:** Replace sequential in-place operators in the hottest iterative inner loops with a single mathematical array expression assigned directly back to the target view using the `[:]` slice operator (e.g., `p_new_center[:] = ((p_old_right + p_old_left) * mult_y_over_x + p_old_up + p_old_down - rhs_eff) * mult_x`). This reduces the Python-level operation count and significantly improves solver execution speed (up to 30-40% faster).

## 2026-04-13 - Python Loop Check Hoisting and Loop Unrolling
**Learning:** In tight iterative Python numerical loops (e.g. `solve_jacobi`, `solve_sor`), having branches like `if it % 2 == 0:` to swap references inside the loop or checking loop invariants like `if mult_y_over_x == 1.0:` per iteration adds compounding interpreter overhead. Additionally, contrary to what was previously learned about implicit temporaries, on smaller grids `np.max(np.abs(p1 - p2))` executes faster in C than performing multiple Python calls to `np.subtract(..., out=tmp)` and `np.abs(..., out=tmp)`.
**Action:** Hoist constant checks out of the loops (e.g., branch on `mult_y_over_x == 1.0` *before* the `for` loop). Unroll iterative swaps (like ping-ponging between `p1` and `p2`) by processing both cases in a single loop body with `range(0, max_iter, 2)`, avoiding swapping logic entirely. Prefer single concise `np.max(np.abs(...))` calls for periodic convergence checks instead of sequence-of-ufuncs on pre-allocated buffers.

## 2024-04-20 - Inverse Multiplication vs Division
**Learning:** In heavily used NumPy array operations (like FVM grid operators such as compute_divergence, compute_gradient, or compute_laplacian), element-wise floating-point division by a scalar is significantly slower than element-wise multiplication by a scalar.
**Action:** Always pre-calculate scalar inverses (e.g., `inv_dx = 1.0 / dx`, `inv_dx2 = 1.0 / dx**2`) and multiply the arrays instead of dividing them. This provides a measurable speedup across the board for mathematical operations with minimal effort and no loss of code readability.
## 2026-04-29 - [Hoisting Invariants out of Tight Python Solver Loops]
**Learning:** The Python interpreter overhead of evaluating invariant branch checks (`if mult_y_over_x == 1.0` or `if omega != 1.0`) on every iteration inside a tight iterative FVM solver loop (like Jacobi or SOR, running thousands of times) represents a measurable performance penalty. Even if the array operations themselves are optimized with `[:]` assignment or `np.putmask`, the sheer cost of looping and repeatedly evaluating simple Python conditionals limits the solver speed.
**Action:** When optimizing tight iterative numerical loops, manually apply "loop unswitching": duplicate the loop bodies to handle all permutations of the invariant conditions outside the loop, rather than branching inside the loop body. This drastically reduces interpreter overhead per iteration, producing immediate execution time improvements (in our SOR solver, testing showed loop time decreased by approximately 2s per 50 runs just from unswitching 2 invariants).
## 2025-05-01 - [Refactoring multi-step putmask updates inside SOR iteration]
**Learning:** In tight iterative loops (like Red-Black SOR), converting multi-step assignments and `np.putmask` into a single mathematical expression (or `np.where`) may actually degrade performance because implicit arrays must be allocated repeatedly. Instead, the correct performance pattern is to use in-place mathematical functions (like `np.add`, `np.multiply`, `np.subtract` with `out=` arguments) targeting a pre-allocated array (like `p_gs`), paired with a final `np.putmask`. This minimizes Python overhead and avoids memory allocations inside the `max_iter` loop, which significantly speeds up convergence.
**Action:** When refactoring iterative FVM loops for performance, do not use single array expressions with `+` or `*` or `np.where`. Pre-allocate all necessary buffers outside the loop, and use `np.add(A, B, out=C)`, `np.subtract`, `np.multiply` inside the loop to avoid allocations.

## 2024-05-18 - Factoring Uniform Grid Operations in Discretization
**Learning:** In FVM spatial discretization functions like `compute_laplacian`, `compute_divergence`, and `convection_term`, the terms are typically evaluated as `(delta_X) * inv_dx + (delta_Y) * inv_dy`. While array multiplication by inverses is faster than division, computing this on square uniform grids (`dx == dy`) still involves two separate full-array multiplications by the same constant, which unnecessarily consumes memory bandwidth.
**Action:** In spatial operators (`fluxion/discretization.py`), use conditional branching (`if inv_dx == inv_dy:`) to factor out the scalar multipliers into a single combined array expression (e.g., `(delta_X + delta_Y) * inv_dx`). This eliminates redundant array multiplications dynamically and provides an immediate ~20-30% execution time improvement specifically on uniform square grids without sacrificing support for generic rectangular grids.
