## 2024-05-24 - NumPy Array Allocation and Strides
**Learning:** Using `np.empty_like(slice)` for temporary memory allocation on a non-contiguous slice (like `array[1:-1, 1:-1]`) defaults to inheriting the memory order of the slice (`order='K'`). Since the slice is often non-contiguous, `np.empty_like` allocates a non-contiguous array, which drastically degrades performance of subsequent chained in-place operations (`out=buf`) due to poor memory access patterns.
**Action:** When allocating intermediate contiguous buffers, always use `np.empty(slice.shape)` explicitly instead of `np.empty_like(slice)`. This ignores the slice's strides and guarantees a fast C-contiguous array allocation.
## 2024-06-27 - [Performance Anti-Pattern: Micro-optimizations in Cold Paths]
**Learning:** Chained in-place NumPy operations (e.g., `np.add(..., out=tmp)`) are an anti-pattern in cold paths (like outer simulation steps). The Python wrapper overhead from calling multiple NumPy functions in sequence outweighs the memory allocation overhead of standard vectorized expressions (e.g., `tmp = a + b`), ultimately reducing performance while severely sacrificing readability.
**Action:** Only use chained in-place array operations inside highly iterative inner loops (e.g., Jacobi/SOR solvers) where the repeated implicit allocations would dominate. For outer steps or standard functions, prioritize readability and rely on standard vectorized mathematical expressions which execute entirely on the C backend.
## 2026-07-06 - [Performance Anti-Pattern: Frontend missing lazy loading for images]
**Learning:** For single-page applications or simple HTML sites like `api/index.py`, images are loaded immediately which slows down the initial page render. This frontend performance optimization must be handled explicitly by Bolt, as UX/A11y (Palette) should not implement performance improvements like `loading="lazy"` or `decoding="async"`.
**Action:** When inspecting frontend performance, look for `<img>` tags, especially those below the fold or used as large artifacts, and add `loading="lazy"` and `decoding="async"` attributes to significantly improve time-to-interactive and initial load performance.
## 2026-07-16 - Math Refactoring in Hot Loops
**Learning:** In purely eager-execution Python environments (like standard NumPy without Numba or JAX), writing mathematically equivalent but un-factored expressions (like `2*k2 + 2*k3`) forces the library to allocate separate intermediate arrays for each scalar multiplication before adding them.
**Action:** When implementing mathematical algorithms (like RK4 integrations) in hot loops, explicitly pre-compute scalar constants (like `0.5 * dt`) and aggressively factor equations (e.g., `2.0 * (k2 + k3)`) to minimize implicit array creations. Use float constants (e.g. `2.0` instead of `2`) to prevent potential overhead from implicit integer upcasting.
## 2026-07-18 - Avoid np.meshgrid in Hot Loops
**Learning:** Using `np.meshgrid()` inside performance-critical, highly iterative loops (like SOR solvers) causes significant slowdowns because it allocates large intermediate 2D arrays on every iteration.
**Action:** When generating coordinate grids or masks (like checkerboard patterns) in hot paths, utilize NumPy broadcasting (e.g., `idx = np.arange(1, nx-1)[:, None] + np.arange(1, ny-1)[None, :]`) instead. This technique computes the necessary indices virtually without allocating large intermediate mesh grid arrays, yielding substantial speedups.

## 2026-07-20 - [Performance Pattern: Array Pre-allocation for Iterative Solvers]
**Learning:** In numerical solvers with iterative time-stepping loops (like Navier-Stokes), allocating temporary arrays locally within the step method introduces overhead from repeated allocation and garbage collection on every time step.
**Action:** Pre-allocate intermediate derivative or buffer arrays at the instance level during initialization (e.g., in `__init__`) and reuse them across iterations to eliminate the overhead of repeated allocations in the hot path.
